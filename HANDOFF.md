# Handoff — Run Plan Tracker

Everything a fresh session needs. Written because session scope could not be
widened to this repo mid-flight, so the work has to move rather than the access.

---

## 1. The setup

- **Watch:** Samsung Galaxy Watch 4 (Wear OS). Does not pair natively with an
  iPhone at all.
- **Phone:** iPhone.
- **Bridge** (Orien Labs) is the third-party app currently getting watch data
  onto the phone, into Apple Health.
- **Strava:** not connected. Ruled out by the owner.
- **Wanted, exactly:** run, distance, time, pace (**splits and average**),
  heart rate, VO<sub>2</sub> max. Nothing else.

## 2. Platform facts already established — do not re-litigate

These were checked against sources during the original session. Several are
counter-intuitive and cost real time to pin down.

| Claim | Consequence |
|---|---|
| Samsung Health does not expose sleep stages or VO<sub>2</sub> max to third-party Wear OS apps | No app can read Samsung's VO<sub>2</sub> figure. Not Bridge, not a custom one. |
| Health Connect does not run on Wear OS | No route to Samsung Health's database from a watch app |
| Strava only imports activities from the **native Apple Workout app**, within 30 days | Bridge → Apple Health → Strava is a dead end by design |
| Apple Health "Cardio Fitness" (VO<sub>2</sub>) is generated by Apple Watch hardware only | It will never populate from a Galaxy Watch by any route |
| Apple Health has no per-km splits for third-party workouts | Importing from Health yields distance, duration, HR — never splits |
| iOS Safari supports neither Web Bluetooth nor any HealthKit web API | A PWA structurally cannot read the watch or Apple Health |
| Samsung Health has no per-run TCX/file export | A custom watch app is the only route to a TCX |

**Net:** VO<sub>2</sub> must be *computed*, and splits must come from a file
off the watch or be typed by hand. There is no third option.

## 3. What was built

`BradLeeDogg/Run-Plan-Tracker-Bridge` — a single-file offline PWA, installable
to the iPhone home screen. Vanilla JS, no build step, no dependencies, no
network calls, `localStorage` only (key `runplan.v1`).

Files, all at **repository root** (paths are relative so Pages works from a
project subpath):

```
index.html  manifest.json  sw.js  icon.svg  icon-180.png  icon-512.png  README.md
```

Two local commits exist — `be925d1` (base app) and `54935c0` (splits, HR,
VO<sub>2</sub>, import). **Neither was ever pushed.** See §5.

**48 automated Playwright checks pass** in an iPhone 13 viewport, covering the
plan maths, log flow, all four guard behaviours, offline rendering, and every
import path.

### Tracked per run
distance, duration, average pace, **per-km splits**, **average heart rate**,
**estimated VO<sub>2</sub> max**, plus completed/skipped, effort, and pain with
a body-area tag.

### The four guards
- over 110% of a week's planned volume → warning
- running long in a recovery week → confirm before saving
- same pain area twice in 14 days → persistent banner, self-clearing
- a week missed entirely → offers to shift the remaining plan forward

## 4. Technical decisions worth knowing

**VO<sub>2</sub> max is estimated, not read.** Pace → oxygen cost via the ACSM
running equation (`-4.60 + 0.182258·v + 0.000104·v²`, v in m/min), then scaled
by heart rate reserve, since %HRreserve tracks %VO<sub>2</sub>reserve. Same
method Runalyze uses. Needs HRmax/HRrest, editable under Stats, defaults
190/55.

**Split origin.** Splits are interpolated across the trackpoint that straddles
each kilometre mark. Devices do not always emit a point at distance zero — when
they don't, the origin comes from the TCX `<Id>` start time, falling back to
extrapolation across the first segment. Without this the opening split is short
by however far the watch had already travelled. This was a real bug, caught in
testing; verified splits come back exact against known source paces.

**Import** accepts TCX, GPX, CSV, JSON. Units are inferred (>200 ⇒ metres,
<600 ⇒ minutes), so everything is shown for confirmation before writing.
Activities pair with the nearest plan run within 3 days. Already-logged slots
are flagged and left unticked. Parsing happens in the page; nothing uploads.

**Logs key on run ids** — `state.logs[runId]`, not on position. They used to key
on `week-day` slots, which meant deleting or reordering a week silently
re-pointed every later log onto a different run. That was fixed when the plan
became editable; ids move with the run, so weeks can be added, removed and
reshaped freely. Do not reintroduce positional keys.

**The plan itself lives in storage**, not in the source. `DEFAULT_PLAN` and
`WEEK1_MONDAY` are only the first-run seed and what "reset" restores. Week
totals are summed from the runs and never stored, so an edited distance cannot
leave a stale total behind. Exports carry the plan alongside the logs, and v1
backups (`week-day` keys plus a `weekStarts` array) are migrated on load and on
restore.

## 6. The other half — getting a TCX off the watch

Lives here, in **`samsung-watch-sync/`**. It used to sit on a branch of
`BradLeeDogg/Writability` — a word processor — purely because the session that
wrote it was scoped to that one repo and had nowhere else to push. It was moved
here, where its other half already is.

A Wear OS app in Kotlin that records runs with GPS and heart rate, computes
splits, writes TCX, and serves it over local Wi-Fi:

- `GET /runs` — JSON list
- `GET /runs/{id}.tcx` — the file
- port **8787**

**The TCX contract is verified, not just eyeballed.** `Splits.kt` and
`TcxWriter.kt` carry no Android imports, so they compile and run on a plain JVM.
Running them against synthetic runs and feeding the output into this app's own
importer showed the two agree: `<Id>` start time, `<Lap>` with
`TotalTimeSeconds`/`DistanceMeters`, `<Trackpoint>` with
`Time`/`DistanceMeters`/`HeartRateBpm`.

That exercise found a real bug. The watch timed its first split from the first
trackpoint, but GPS delivers nothing until it locks, so the opening kilometre
was short by however long that took — 4:56 against a true 5:04, while this app
said 5:04 because it already keys on `<Id>`. Fixed on the watch side; both now
agree. `verify_splits.py` covers the case.

**One known difference, by design:** the watch emits a trailing partial split
(5.4 km gives six laps, the last 400 m); this app reports only whole
kilometres. The tail does not appear in the split list.

**No APK has ever been built, and it cannot be built in this container.** Not
merely a missing SDK: Gradle's `google()` repository *is* `dl.google.com`, which
serves both the SDK packages and the Android Gradle Plugin, and that host is
blocked here — the build dies at plugin resolution before touching any Android
code. `maven.google.com` resolves to the same host. This is settled; do not
re-attempt it. Building needs a machine with ordinary access to Google's
servers: Android Studio, developer mode on the watch, ADB over Wi-Fi.

The Gradle wrapper is now committed (8.9, suiting AGP 8.5.2), so `cd
samsung-watch-sync/wear && ./gradlew :app:assembleDebug` works from a clean
checkout with only a JDK 17–21 plus the SDK that Android Studio provides.

**Constraint to remember:** the PWA on GitHub Pages is HTTPS and browsers block
HTTPS pages from fetching `http://`. So it cannot pull from the watch in one
tap. The flow is: Safari to `http://<watch-ip>:8787/runs`, download the `.tcx`
to Files, then Import in the app. Two steps, about a minute.
